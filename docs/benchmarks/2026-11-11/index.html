How this was measured

  • CMake Release builds: -O3 -DNDEBUG. One server event loop and a separate C load-generator process. No TLS, access logging, workers, or pipelining.
  • Persistent HTTP/1.1, one in-flight request per connection. Connections open before timing. Request/response I/O and client scheduling are timed; connect time and latency sorting are excluded.
  • 5,000 warmup requests before every measured run. Three rounds; each configuration sends the request count recorded in the CSV. Backends run sequentially; the first round runs forward, the second reverses workload/concurrency order.
  • Any HTTP status, framing, connection, or stall failure aborts collection. Counts exclude warmup requests. The generator checks status and length, not body content.

How to read the results

More connections can increase throughput while increasing per-request latency. The fastest point is a property of this workload and machine, not a universal tuning recommendation.

The client and server share CPU, memory, and the loopback stack. The poll-based client can become the bottleneck. No CPU pinning, machine isolation, or randomized backend order was used; differences between backends are descriptive, not causal.

SQLite here is an in-memory, read-only fixture. It measures adapter and query/serialization cost, not disk persistence, contention, write durability, or the complete Notes app. Tail latency and production capacity need longer tests from another host.
